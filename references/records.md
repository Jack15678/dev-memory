# 记录格式与归属

三份长期文档固定为 HISTORY、DECISIONS、KNOWLEDGE。没有条目时保留标题和「暂无记录」，不要填入虚构示例。下列模板中的括号内容按实际证据填写，通常一条 5～10 行即可。

## HISTORY.md：发生了什么

```markdown
<a id="h-001"></a>
## H-001 · 日期 · 一个完整任务
- 目标与验收：（本次需要达成的行为）
- 状态：（进行中 / 已完成；实现和验证分开描述）
- 行为变化：（之前 → 之后）
- 原因：（直接原因，或引用 D-xxx）
- 涉及位置：（相对项目路径、符号名）
- 尝试与证据：（仅列有后续价值的失败路线及重试条件）
- 验证：（仅测试存在 / 历史运行 / 本轮运行；工作目录、命令、结果及未覆盖范围）
- 验证对象：（实际受测提交；或基线提交 + 相关未提交/未跟踪改动的路径与摘要）
- 版本：（未提交 / 无初始提交 / 随包含 H-001 的提交保存）
```

跨文件引用用 `[D-001](DECISIONS.md#d-001)`。修改过的代码未提交时，旧 HEAD 只能是基线；不要把它标为本次版本。实际写入时使用事件发生日期；补记时注明记录日期，未知历史日期不要猜。

「版本」说明记录如何保存，「验证对象」说明结果适用于哪份代码，两者不能互相替代。未执行的测试只记录存在；引用旧日志时注明历史来源与其受测版本。没有初始提交时写「无提交基线」并列相关工作区改动；无法确定受测版本时写未知。验证后相关代码又有修改，原结果只覆盖此前对象，新增部分保留验证缺口。

## DECISIONS.md：后续开发需要理解什么

```markdown
<a id="d-001"></a>
## D-001 · 日期 · 采用的选择
- 状态：（提议 / 已采用 / 已否决 / 被 D-xxx 替代 / 已撤销）
- 来源：（用户明确决定 / agent 在授权内选择 / 事后推测；具体依据）
- 适用范围/读取时机：（可选；一句话说明修改哪些模块、符号或行为前应读）
- 背景与约束：
- 实际考虑过的选项：
- 选择与理由：
- 接受的代价：
- 重新评估或移除条件：
- 实现入口：（相对路径 + 函数/常量名；特殊值及依据按需记录）
```

只列确实考虑过的选项。事后想到的替代方案标为后续建议。推翻决定时创建新 D 条目并在旧条目中建立替代链接；不要抹掉旧理由。记录硬编码值时，无测量依据就写无测量依据，不把产品取舍伪装成性能结论。

## KNOWLEDGE.md：哪些经验可以复用

```markdown
<a id="k-001"></a>
## K-001 · 日期 · 可复用的方法或想法
- 成熟度：（本项目已验证 / 待验证 / 已否定）
- 问题与方法：
- 适用条件：
- 不适用或易误用之处：
- 出处与证据：（项目/文件、H/D 编号或实际结果）
```

记录可核验的结论与简短理由，不保存模型内部思考链。不要复制秘密、完整环境配置和无关私人聊天。知识笔记留在当前项目；导入个人知识库需另有请求。

## 归属示例（虚构，不是项目事实）

用户说「首版上传上限 20 MiB，以后有大文件需求再考虑调整」。

- D-001：完整记录固定上限的选择、理由、代价与重审条件；常量位置和值也在这里。
- H-001：记录「增加大文件提示」、实际验证和提交关系，引用 D-001，不再复制完整解释。
- KNOWLEDGE：没有新的可复用经验，可以保持不变。

如果用户下一轮只问「大文件提示现在怎么显示」，读取记录和代码回答即可。若用户改为「现在需要支持 100 MiB」，新建 D-002 取代 D-001；有代码改动时再记录 H-002。

若只发现代码已变成 100 MiB，却找不到改变上限的有效决定，记录「实现为 100 MiB，与 D-001 冲突」；D-001 的已采用约束和旧理由仍保留，不能据代码变化倒推用户已经批准。
